# Loan Portfolio Data Migration & Data Quality Pipeline

A portfolio project that will migrate messy, **synthetic** loan portfolio CSV
exports into a normalized relational database, with data quality checks,
rejected-record reports, and reconciliation.

**Current status: Phase 2 complete (synthetic data generator).** Setup and
reproducible messy CSV exports are ready. Cleaning, validation, database loading,
and reconciliation are planned for later phases.

## Why I am building this

I am a Business Informatics student preparing for data-related internships.
This project will demonstrate how I approach legacy data cleanup, relational
integrity, migration validation, and explaining results to reviewers.

All customer, loan, and payment data will be generated by a script. No real
personal or company data belongs in this repository.

## Planned workflow

Synthetic legacy CSVs → extract → transform → validate → transactional load
→ reconciliation report.

The target database will have `customers`, `loans`, and `payments` tables.
Rejected records will include a named rule and a readable reason. The report
will account for each source record.

## Tech stack

Python 3.11+, pandas, SQLAlchemy, SQLite, Faker, pytest, and ruff.
`python-dotenv` will support local configuration; PyMySQL will support the
optional MySQL connection through `DATABASE_URL`.

## Set up locally

Run these commands from the repository root with Python 3.11 or newer.

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
```

If Windows uses the Python launcher, use `py -3 -m venv .venv` for the first
command. Calling the environment's interpreter directly requires no shell
activation or execution-policy changes.

### macOS / Linux

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
.venv/bin/python -m pytest
.venv/bin/python -m ruff check .
```

The requirements install the local package in editable mode, so imports work
from the `src` layout without setting `PYTHONPATH`.

`.env.example` documents the planned configuration. Configuration loading and
the `generate`, `run`, and `report` commands will be implemented in later phases.

## Generate synthetic legacy data

The standalone generator is available now; the unified CLI comes in Phase 7.
Use an explicit output directory so the script has no hardcoded data path.

```powershell
.\.venv\Scripts\python.exe -m migration.generate_legacy_data --output-dir data/legacy
```

On macOS / Linux, use `.venv/bin/python` instead. The default is 1,000 base
customers with seed 42. To change the size or seed:

```powershell
.\.venv\Scripts\python.exe -m migration.generate_legacy_data --output-dir data/legacy --customers 100 --seed 7
```

`--size` is an alias for `--customers`. The size must be at least 1. Running the
generator again replaces the three CSVs in the chosen directory. With the same
size, seed, and pinned Faker version, their bytes are reproducible; dates do not
depend on the current day. `.env` settings are not consumed by this standalone
command yet.

| Default export | Rows | Contents |
| --- | ---: | --- |
| `customers_legacy.csv` | 1,100 | 1,000 base customers + 50 exact + 50 probable duplicates |
| `loans_legacy.csv` | 1,000 | One loan per base customer, with deliberate orphan references |
| `payments_legacy.csv` | 2,000 | Two payments per loan, including deliberate invalid payments |

The exports include three date formats, inconsistent name casing and whitespace,
empty fields, invalid emails and country codes, currency-formatted amounts,
inconsistent loan statuses, negative payments, and payments before loan start.
All valid-looking emails use the reserved `example.com` domain.

Defects are injected in repeating blocks of 20 base customers. Sizes of 20 or
more include every defect category; smaller sizes include a subset. Spelling
variants alternate with casing variants across blocks, so both appear at 21
base customers or more. These are controlled test fixtures, not estimates of
real-world data quality.

The tracked [tiny sample](data/legacy/sample/) was generated with 10 base
customers and seed 42 (12 customer rows, 10 loan rows, and 20 payment rows):

```powershell
.\.venv\Scripts\python.exe -m migration.generate_legacy_data --output-dir data/legacy/sample --customers 10 --seed 42
```

The full exports remain ignored by Git. Generation does not clean records or
create a database.

## Implementation phases

1. **Setup — complete:** structure, configuration examples, package skeleton,
   documentation, and import smoke tests.
2. **Data generator — complete:** reproducible messy CSVs and a tiny synthetic sample.
3. Extract and transform: standardize fields and identify duplicates.
4. Validate: named rules and rejected-record reports.
5. Load: constrained schema, transactions, and idempotent loading.
6. Reconcile: counts, rejection breakdown, and a PASS/FAIL accounting check.
7. CLI and tests: commands and meaningful end-to-end checks.
8. Documentation: architecture diagram, usage examples, and example report.
